# 下 MQTT 指令前必須先確認設備身分（2026-09-23 事故）

## 鐵則

**未經實體管道確認設備身分之前，絕不對任何設備發出會造成物理動作的指令。**

公共 broker 上訂閱 `hoban/+/status` 掃出來的每一台，都是**正在運作中的現場設備**，
不是測試機。繼電器動作 = 閘門動作 = 嚇到現場的狗，而且**關上的門切不回去**。

## 事故經過

2026-09-23 診斷一台「接 USB 正常、電池不正常」的 hoRelay2 時：

1. 訂閱 `hoban/+/status` 掃到多台線上設備，把掃到的設備 ID 列成選項請使用者挑
2. 使用者挑了 `hoban-10b41d4afeac`，實際手上那台是 `hoban-10b41d4afe40`
3. 對 afeac 發 `ON` → `pulseRelay()` 點動 2 秒 → **現場閘門關上、嚇到狗、無法復原**

**根本錯誤不是「挑錯」，是把設備識別的責任丟給使用者用選單挑。**
MQTT 掃到的 ID 無從驗證哪台在對方手上，那份清單不構成識別依據。

順帶一提，afe40 根本不在 emqx，而在 mqttgo.io——用單一 broker 掃到的清單
連「使用者那台有沒有在裡面」都不保證。

## 指令分級

| 指令 | 後果 | 可否用於身分確認 |
|---|---|---|
| `status` | 只重發一次 status，不動任何腳位 | ✅ 安全 |
| 純訂閱監聽 | 完全不送封包 | ✅ 安全 |
| `ON` | `pulseRelay()`：繼電器吸 2 秒、LED 亮 2 秒 | ❌ 物理動作 |
| `OFF` | `relayOff()`：切斷繼電器 | ❌ 物理動作 |
| `reset` | `clearWiFiConfig()`＋重啟 → 進 BLE 配對模式，**要重新配對才能回來** | ❌ 等同變磚 |
| `update:{...}` | 觸發 OTA | ❌ 高風險 |

## 正確做法

確認身分，任選其一（都不碰繼電器）：

- **序列埠開機 log**：`.\monitor.ps1`，設備啟動時會印自己的 device ID
- **App 端**：請使用者從 App 上讀出設備 ID／名稱
- **發 `status`**：無害，可用來比對回應內容

驗證繼電器行為，優先用不發指令的做法：

- **純監聽 + 請使用者自己從 App 按一次**，觀察 `device.relay` 欄位跳 1→0。
  完全不需要由 agent 發指令。
- 真的要由 agent 發 `ON`，必須「身分已確認」**且**「使用者知道繼電器會實際動作並同意」，
  兩個條件同時成立。授權本身不能替代身分確認——2026-09-23 那次是有授權的。

## 順帶可用的無害診斷訊號

`status` 裡缺不缺 `battery` 欄位，就能判斷 `batterySenseAvailable`
（見 `addBatteryToStatus()` 的 `if (!batterySenseAvailable) return;`）——
1.8.5 以上卻沒有 `battery`，代表開機時 GPIO 1 讀值 <600mV、分壓模組沒供電。
這類判斷全部只靠訂閱就能做，不必發任何指令。
